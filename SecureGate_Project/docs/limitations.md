# Limitations

What SecureGate and its current evidence do **not** show. Each item says where it comes from.

## Engine

1. **The engine sees only what the scanner reports.** Semgrep 1.180.0 gave no error and no skipped entry for a Python file with a syntax error (EXP-00 SG04), so that file was silently not analysed and the gate cannot detect it. EXP-01 confirmed this with real binaries: `--strict` and `--verbose` do not report it either, and it is the only fault left that passes under S2/S3 (3 of 81 faulted L2 runs).
2. **pip-audit uses one exit code (1) for "vulnerabilities found" and for crashes.** The engine separates them by reading the report (exit 1 with empty stdout = NO_OUTPUT; exit 1 with no vulnerabilities = INCONSISTENT_EXIT under S2/S3). Under S0 these cases are indistinguishable (EXP-00 PA03).
3. **A requirement that does not exist on PyPI makes pip-audit fail, not skip** (EXP-00 PA03), so the fault catalogue's F9 for pip-audit (`skip_reason`) occurs only with other skip causes; the L3 realisation gives NO_OUTPUT instead (EXP-01: the run is still stopped, with a different label).
4. **Coverage for Gitleaks is read from its log text** ("N commits scanned", "not a git repository"). A future Gitleaks version that changes these messages would break this check; `tests/test_live_outputs.py` replays the real messages and would fail.
5. **Registry rule packs are not content-hashed.** Semgrep does not expose a pack version, so a `p/python` result is identified by pack name, Semgrep version and date only (DEC-009). Experiments use a committed local rule file instead.
6. **The pip-audit vulnerability database is online and changes.** The same requirements file can give different findings on different days (EXP-00: `flask==3.0.3` had 2 known vulnerabilities on 17 Nov 2026).
7. **S1 is not uniformly safer than S0** (DEC-006): for an exit code that claims findings while the report lists none, S0 blocks and S1 passes, because consistency is only checked from S2.
8. **Redaction is pattern-based** (FR-29). It covers common token formats and `key=value` secrets; an unusual secret format in a tool's error message could pass through. Gitleaks itself runs with `--redact`.
9. **Only Python projects, three tools, GitHub Actions.** Other ecosystems, scanners and CI systems need new adapters or workflows.

## CI integration

10. **An invalid policy is stopped by the Tests job** (the repository-policy test) before the gate step, so the gate's own exit-3 path is verified by unit tests and local runs, not by a CI gate step (validation branch `semester8-ci-validate-config`).
11. **Validation used a public repository and GitHub-hosted runners.** Self-hosted runners, private repositories and branch-protection rules (required checks) were not configured; making the SecureGate job a required check is a repository-settings change that needs the owner's approval.
12. **The vulnerable-dependency and missing-tool validations are deliberate misconfigurations on validation branches**, not real incidents.

## Experiments (EXP-01 pilot)

13. **Pilot, not the study.** The protocol is not frozen; the cell set, repetitions and the clean control may change after guide review.
14. **Injected, not field-frequency, faults.** Rates such as SPR describe this cell set; they are not estimates of how often scanners fail in practice. Wilson intervals are over runs of a designed (not random) cell set.
15. **L1 is simulated.** It replays real recorded outputs with deterministic edits; it shows how the decision logic behaves, not how real tools fail. L1 and L2 results are never pooled.
16. **Small control sets** (one clean target; one known finding per scanner), so FBR and CBR have wide intervals.
17. **Timing on shared hosted runners is noisy**; overhead is reported as medians with interquartile ranges, and the evidence-validation time is measured inside the engine, separately from scanner execution.
18. **Same author builds and evaluates.** Mitigations: expected outcomes written before the run (`protocol.json`), raw data kept, results generated by scripts.
